# ARCHITECTURE.md — tabletop-craft-ar

A live Java-edition block world shown as a miniature on a real table in Quest 3 passthrough AR. Java players see the headset user as a giant inside the world.

Related: idea file [VR-7](https://github.com/NickStassen/ideas/blob/master/vr/07-minecraft-ar-tabletop.md) and sister project [ironman-quest3-hud](https://github.com/NickStassen/ironman-quest3-hud), which has the Unity/Meta XR setup this project reuses. The wire format is in [PROTOCOL.md](PROTOCOL.md), the phases in [PLAN.md](PLAN.md), and the sources in [RESEARCH.md](RESEARCH.md).

## 3. Server plugin

### 3.1 Threading rules (hard)
- The Java-WebSocket server runs its own selector/worker threads. **No Bukkit API calls on those threads.** Every inbound message is parsed there (pure JSON → record) and then handed over:
  - poses go into an `AtomicReference<Pose>` latest-value slot that the main-thread tick task reads (so stale poses are dropped for free);
  - `subscribe`, `avatar_config` and similar go into a `ConcurrentLinkedQueue<Command>` that the main thread drains each tick.
- Outbound: main-thread code builds a payload object and calls `conn.send(String)` (Java-WebSocket's `send` is thread-safe). JSON serialization of large snapshots happens **off** the main thread.
- One repeating task, `runTaskTimer(plugin, 1, 1)`, drives the tick work: drain commands, apply the latest pose to the avatar, flush the batched block changes, and send player positions every 2 ticks.

### 3.2 RegionExporter (chunk_snapshot)
1. On the main thread, for each chunk that overlaps the region, take `chunk.getChunkSnapshot(false,false,false)`. Paper copies the section palettes here; that's cheap (about 2 chunks × 4 for 32x32). If a chunk isn't loaded, load it with `world.getChunkAtAsync(x,z)` first.
2. Async (the reader's own worker pool, see 6): walk the region in yzx order with `snapshot.getBlockData(lx, y, lz)`, build the palette and RLE (PROTOCOL §6), serialize the JSON and send it. `ChunkSnapshot` is immutable and documented as safe to use off-thread.
3. Snapshot ids are per connection. Block changes that arrive while a snapshot is being built are buffered and replayed against the new `snapshot_id`.
4. Light and biomes (PROTOCOL §4.5.1) are read only when a session on that region has `light_v1` / `biomes_v1`: `getChunkSnapshot(false, biomes, false, light)` (Paper's 4-argument form; without extras it now skips copying light, which made the main-thread step 3-4x cheaper), and the same async walk packs `sky << 4 | block` per block and samples one biome per 4x4x4 cell. Climate (`World#getTemperature/getHumidity`) is looked up on the main thread once per biome key and cached. The light and biome JSON is encoded on the outbound executor (`RegionReader`, `BiomeGrid`, `Protocol.addExtras`).

5. Big regions ([area]): step 1 takes the ChunkSnapshots for at most `stream.snapshot-budget-ms` (1.5 ms) per tick and continues on the next tick; a 288×288 region (361 chunks, about 3 ms warm, 6 ms right after generation) takes 2–4 ticks. A chunk that unloaded in between (regions are only ticketed once set) is loaded again with `getChunkAtAsync` first. A `READS` log line every 30 s sums the main-thread cost of all reads and diffs. `region_request` windows wider than `max_region.view_width` are narrowed around their centre by whole sections (`RegionCaps.clampView`, PROTOCOL.md 4.25), and `SectionCodec` sends a resize as a delta against the session's last grid (other dims, section-aligned shift).

6. Region moves ([nav], `RegionMerge`): a `region_request` whose new region overlaps the session's old one in the same world reads only the sections that weren't fully inside the old region. Only the chunks holding those sections are captured (one row of 22 chunks for a one-section shift at 352 wide, in the same tick when they're loaded, which `stream.ticket-ring` makes likely), the walk fills just those sections, and every other section is copied from the session's last grid, light and biomes (what the headset has). The delta then lists exactly the sections read, without an O(volume) compare, and only those sections are remapped to the session palette. The copied sections are as old as that grid: while a move is read, diffs of the shared region are held back (they would change the base it copies from), and once it is sent the region is diffed again if anything was marked dirty since the base was captured. Walks run on the plugin's own three-thread pool (Bukkit's async scheduler only starts tasks on its next 50 ms heartbeat). A one-section shift of 352×160×352 takes one tick on the server: 0.2–0.5 ms of main thread, a 22–42 ms walk, a 0.5–1.2 MB delta (TESTING.md "Faster gliding"). The `region_request` size check scales the previous region's estimate to the kept volume and adds the new sections' own estimate. Biomes count only towards part 0 when a sectioned snapshot is split into parts.

### 3.3 BlockChangeTracker (block_update)
- Event listeners at MONITOR priority with ignoreCancelled: `BlockPlaceEvent`, `BlockBreakEvent`, `BlockPhysicsEvent` (sampled), `BlockFromToEvent`, `BlockBurnEvent`, `BlockFadeEvent`, `BlockFormEvent`, `BlockSpreadEvent`, `LeavesDecayEvent`, `EntityExplodeEvent`, `BlockExplodeEvent`, `BlockPistonExtendEvent`/`RetractEvent`, `EntityChangeBlockEvent`. Events fire **before** the change, so record only the *position* and read the state at end of tick (in the next tick task, 1 tick later).
- Safety net: every 20 ticks, re-snapshot the region's chunks async and diff them against the last sent state. That catches `/fill`, `/setblock` and WorldEdit. It's cheap at this size (65k comparisons).
- Coalesce by position. Emit one `block_update` per tick; past 4096 changes, send a new snapshot instead.
- Light: for `light_v1` sessions the diff also compares packed light against what the session last got and sends changed cells in `block_update.light` (possibly with no block changes). Light settles a little after the change event, so a change event also schedules a second diff 4 ticks later; past 16384 light changes the session gets a new snapshot.

### 3.4 PlayerBroadcaster
Every 2 ticks: for online players in the region's world within the region's XZ bounds plus 16, send pos/yaw/pitch/sneaking. The skin URL comes from `player.getPlayerProfile().getTextures().getSkin()` and goes out once per UUID, with `skin_model` (`wide`/`slim`, from `getSkinModel()`). Offline-mode servers have no textures, so `skin` is null there.

### 3.5 GiantAvatar (decision)
**Default (`avatar.placement: floating`): a giant player head and two hands, no body, exactly where the headset and controllers are relative to the table.** Two Mannequin modes (`ground`, `exact`) stay available.

Why: on the first headset session the user found the ground-standing Mannequin wrong in two ways. Its hand cubes looked "glued to the chest", and its height didn't match where their head was above the terrain. A body can't follow both the exact head pose and the terrain at once, and the Mannequin's arms can't be posed. A floating head plus hands can be exactly right at any table scale.

- **Floating** (pure maths in `GiantPlacement`, unit-tested):
  - Head: an `ItemDisplay` showing a `player_head` with the user's profile in the `PROFILE` data component (the resolved, signed profile, or the bare name, which clients resolve). It sits at `origin + p / block_size_m` and is sized like a real head (`avatar.head-size-m` 0.25 m, so 25 blocks at 1 cm/block). Above `avatar.max-head-blocks` (64) the head and hands shrink by the same factor and `avatar_state.note` says so.
  - Head orientation: the `Transformation` carries the full headset rotation, roll included; the entity's own yaw and pitch stay 0. The tabletop frame's axes are the world's and both are right-handed (PROTOCOL §3), so the left rotation is the pose quaternion unchanged. The right rotation is a fixed 180° about Y. With the FIXED item transform, the game draws a player head centred on the entity and facing +Z: item displays add a 180° Y turn, and `template_skull`'s `fixed` transform adds another plus a 4/16 lift. The 180° right rotation brings the face to −Z, the pose frame's identity "forward". Checked against the 26.3 client code and unit-tested: the face follows `Pose.forward()` for any orientation.
  - Hands: `ItemDisplay`s at the mapped controller poses, turned with them. Each is a flat box (0.8 × 0.45 × 1.0 × `avatar.hand-size-m`, 0.1 m), long side along the controller's forward axis, so it reads as a hand and shows the controller's orientation. Its block is the plain block closest to the hand colour on the user's skin (`HandColour`: the skin PNG is downloaded off-thread after the lookup, and the right arm's bottom face and lowest rows are averaged and matched against 75 block colours measured from the 26.3 textures). Without a skin it uses the default skin's hand colour; `avatar.hand-block` overrides the choice. A player head would put a face on each hand.
  - Smoothing: none on the server, because the displays interpolate on the clients (`setTeleportDuration` and `setInterpolationDuration` = `avatar.interpolation-ticks`, 2 ticks, with interpolation delay 0 on every update).
  - Visibility: view range 8 (512 blocks at default entity distance), since the head can be 100+ blocks above the players. Brightness is fixed at 15/15, so a head whose centre is inside terrain isn't drawn black. The server's `entity-tracking-range.display` (spigot.yml, 128 blocks horizontally) still limits who receives the entities.
- **Mannequin modes**: a `Mannequin` scaled with the `SCALE` attribute and two `ItemDisplay` hands. The "true" scale is `(user_height_m / block_size_m) / 1.8`, clamped to `max_scale` (16, so 28.8 blocks).
  - `ground`: X/Z of the mapped head, clamped into the region (0.5 block inset). The feet stand on the highest `MOTION_BLOCKING_NO_LEAVES` surface over the footprint. Hand offsets are scaled by `giant height / user_height_m`.
  - `exact`: the head is at the mapped head position and the hands at the mapped hand positions, with the feet 1.62 × scale below the head.
  - Motion: eased in per tick (`avatar.smoothing`, 0.5; jumps over 16 blocks snap). The body yaw lags the head by at most 50°.
- Chunks: the giant's entities are non-persistent, so moving them into an unloaded chunk deletes them. The plugin keeps plugin tickets on the region's chunks and on the chunks of the giant's last pose. A target chunk that isn't loaded is loaded with `getChunkAtAsync` and ticketed as soon as the load completes; with no player nearby it would otherwise unload before the next tick. The giant holds still until then.
- Skin: `skin_player` from `avatar_config`; a blank value falls back to `avatar.skin-player`. The entities first get a name-only (dynamic) profile, which game clients since 1.21.9 resolve themselves.
  - The plugin resolves the name off the main thread with `PlayerProfile.complete(true, true)`, which does an online lookup even on an offline-mode server, and falls back to the Mojang API for name → UUID.
  - It then switches to a static profile with the signed textures, picks the hand block, sets `skin_resolved` and sends `avatar_state`. A failure sends `error skin_failed`. Results are cached per name.
- Lifecycle: spawn on `avatar_config{enabled:true}` (or the first pose), remove on disable, disconnect (+10 s) or plugin disable. The entities are non-persistent, so a crash never leaves giants behind. `/tabletop avatar placement <floating|ground|exact>` switches modes and respawns when the entity set changes.

### 3.6 LinkServer
`WebSocketServer` subclass bound to `config.bind` (default `0.0.0.0:8765`), `setReuseAddr(true)`. It's started in `onEnable` on its own thread and stopped in `onDisable` with `stop(1000)` (close code 4005 to clients). One `Session` object per connection: state machine `AWAIT_HELLO → READY → CLOSED`. The token is compared in constant time (SHA-256 of both, `MessageDigest.isEqual`). At start it logs `Headset URL: ws://<ip>:<port><path> (<interface>)` for each private IPv4 of the PC. `LanBeacon` (config `discovery`) answers the headset's UDP discovery probe on its own daemon thread (PROTOCOL.md §7): LAN senders only, 20 replies/s, values fixed at start plus a volatile player count.

### 3.7 Block edits from the headset (PROTOCOL §4.20)
`block_edit` is parsed on the websocket thread (`BlockEdit`) and rate-limited there with a per-session token bucket (`EditLimiter`, `edit.max-per-second`), so a flood never reaches the main thread. `TabletopPlugin#onBlockEdit` then runs in the tick's command drain: region check, `Bukkit.createBlockData`, the `edit.deny` list and the registry, then `EditWorld` applies it the vanilla way: the world border, replaceability (`EditRules.replaceable`: Paper's `isReplaceable` flag, one snow layer, sculk vein, never by the same block), survival (`BlockData#isSupported`), players and mobs in the way (the state's collision boxes against `World#getNearbyEntities`, minus the giant's entities), persistent leaves, `waterlogged` from the cell, both halves of doors, beds and double plants (`EditRules.partner`, string rules shared with the client; the other half is cleared without physics on a break, so nothing drops), and the placed block's own connections from vanilla `Block.updateFromNeighbourShapes` (Paper has no API for it: called reflectively through `CraftBlockData#getState`/`createData` and `CraftWorld#getHandle` on the unobfuscated server, logged once as `EDIT_SHAPES on|off`, skipped if it ever fails; Paper's `setBlockData` updates the neighbours' shapes but not the placed block's). Then `setBlockData(data, edit.physics)` per cell. A plugin's `setBlockData` fires no block events, so it calls `markDirty` itself and the change goes out through the normal diff (§3.3). Refusals are `error`s carrying the edit's `pos` and a readable message ("stone is in the way"). Main-thread cost per edit is 0.1–0.4 ms (median 0.13 ms).

### 3.7.1 Block registry (PROTOCOL.md 4.24)
`RegistryScan` reads every item with a block form from Paper's registries on plugin start and `/tabletop reload` (main thread, ~0.1–0.2 s once), with the block tags the categories need; `BlockRegistry.build` (pure, unit-tested) drops air, technical blocks, `edit.deny` and feature-disabled blocks, finds the variants (wall torches → torch...), assigns categories from tags and names (Paper has no creative-tab API) and sorts families together. The JSON body (~67 KB) is built once; `onReady` sends a copy right after `welcome`. `onBlockEdit` refuses a `place` whose block isn't a registry block or variant (`bad_state`), after the `edit.deny` check.

### 3.8 Entities and actions (PROTOCOL.md 4.21–4.22)
- `EntityStreamer` runs right after `sendPlayers` (every `stream.players-every-ticks`, 10 Hz) for sessions with `entities_v1`. Each region is sampled once per send even when several headsets share it: `EntitySampler` calls `World.getNearbyEntities` on the region box plus `entities.margin`, drops players, the giant's tagged entities and invisible helper types, keeps the `entities.max` nearest the centre, and reads each into a plain `EntityState` (Paper API only, main thread). Item stacks and equipment are API copies, so they're re-read every 5th sample per entity (spread by id) and cached in between. For living entities the location yaw is the head's (CraftBukkit reports `yHeadRot`) and `getBodyYaw()` the body's.
- `EntityDelta` (pure, unit-tested) diffs the sample against what the session holds: new ids get full entries, known ones only changed fields (thresholds 0.01 block and 1°, so idle mobs cost nothing), gone ids go to `removed`, and a region change sends a full list. The JSON is serialized on the outbound thread, which also counts the bytes for the `ENTITIES` log line (every 30 s: entities, sample and delta ms, bytes/s) and `/tabletop entities`.
- `player_positions` gains `id`, `vehicle`, `pose` and `equipment` (`EntitySampler.playerExtras`), for every client.
- `ActionListener` (MONITOR handlers for `PlayerAnimationEvent`, Paper's `BlockBreakProgressUpdateEvent`, `BlockDamageAbortEvent`, `BlockBreakEvent`, `BlockPlaceEvent`, `Entity/BlockExplodeEvent`, `EntityDamageEvent`) only records into an `ActionBatch` (pure: collapses repeats, caps 128 per tick, filters per region), and does nothing while no session asked for `actions_v1`. `flush` runs every tick and sends one `actions` message per session that has something in its region.

### 3.8.1 A living world (PROTOCOL.md "World state", "Living entities")
- `WorldStateStreamer` (main thread, every tick, a few getters per world in use) builds a `WorldState` record per region world (`World#getFullTime`, `getTime`, `hasStorm`, `isThundering`, `getEnvironment`, `hasSkyLight`, `isFixedTime`, the daylight game rule and the tick manager) and sends `world_state` to `world_v1` sessions when `WorldState.due` says so: nothing sent yet, the world/dimension/weather/clock mode changed, the clock is more than 40 ticks off the client's prediction, or 20 ticks passed. Pure and unit-tested (`LivingTest`).
- `EntitySampler.living` adds the leash holder (Paper `Leashable`), eye height, `CustomNameVisible`, `ChestedHorse`, orb value, the bobber's shooter, the enderman's block, the shulker's peek and face; `EntitySampler.display` reads `Display#getTransformation`, billboard, brightness, item context and (with the cached stacks, every 5th sample) a text display's plain text. Text displays are no longer filtered out; the giant's speech bubble still is (scoreboard tag). `EntityDelta` diffs the new fields like the old (the display as one object; the lid by 0.05).

### 3.9 Chat, commands and server status (PROTOCOL.md 4.26–4.28)
`ControlService` (a `Listener`; config sections `chat`, `commands`, `status`) owns all three; `LinkServer` parses `chat_send`, `command`, `command_complete`, `world_query` and `players_query` on the websocket thread and rate-limits them there (`EditLimiter` with a burst: chat and commands 2/s burst 5, completions 10/s), then queues them for the main thread.
- **Chat in:** MONITOR handlers for `AsyncChatEvent` (off the main thread: it reads only the player's name, uuid and entity id and flattens the message with `PlainTextComponentSerializer`; the JSON is serialised on the outbound executor, and the session list is a concurrent map), `PlayerJoinEvent`/`PlayerQuitEvent`/`PlayerDeathEvent`/`PlayerAdvancementDoneEvent` (their adventure messages, flattened in en_us by Paper's flattener), `BroadcastMessageEvent` (plugin broadcasts; the plugin's own broadcast is skipped while it runs on the main thread), and `PlayerCommandPreprocessEvent`/`ServerCommandEvent` for `/say` and `/me` (no chat event fires for them). `/tabletop tell` (permission `tabletop.tell`, default true; every other subcommand checks `tabletop.admin` itself) whispers to the headsets.
- **Chat out:** `ChatText` (pure, unit-tested) sanitises the operator name (`hello.operator_name` → `[A-Za-z0-9_]{1,16}`, else `chat.default-name`) and the text (no control characters or `§`), and builds `chat.format` with MiniMessage `Placeholder.unparsed`, so a headset can't inject tags. `Bukkit.broadcast` sends it to players and the console; it's echoed to `chat_v1` sessions as `operator`, and `GiantAvatar.say` puts a `TextDisplay` (tag `tabletop_avatar`, billboard centre, about a fifth of the head size) over the giant's head for `chat.bubble-seconds`, moved with the head every tick.
- **Commands:** `CommandPolicy` (pure, unit-tested) resolves the root through `CommandMap#getCommand(label).getName()` (aliases; `namespace:` and `/` stripped) and checks every split after a `run` word of `execute`/`return`, against `commands.allow`/`commands.deny`. Then, on the main thread, `Server#createCommandSender(Consumer<Component>)` (Paper's `FeedbackForwardingSender`: operator level, no admin broadcast) runs the line with `Bukkit.dispatchCommand`; its consumer collects the feedback until the result is sent and turns anything later (5 s) into `command_output`, flushed once per tick. A brigadier syntax error escapes `dispatchCommand` as a `CommandException`; its `CommandSyntaxException` cause becomes the error line. `at` wraps the line in `execute in <dimension> positioned …` (plugin commands run through it too). `say`/`me` become chat. Ops with `tabletop.notify` get a grey `[Tabletop: /line]`. Completion is `CommandMap#tabComplete` with a fresh sender (brigadier suggestions for vanilla commands). Main-thread cost is the command's own (median 0.85 ms, 22 ms for the first one while classes load; logged `CMD … (ms)`, a warning over 50 ms).
- **Status:** `server_status` every `status.every-ticks` from `Bukkit.getTPS()`, `getAverageTickTime()`, `Runtime`, the tick manager and per world `getChunkCount`/`getEntityCount`/`getPlayerCount`/time/weather (built once per send, about 0.2 ms with three worlds); `world_info` reads `Registry.GAME_RULE` with `World#getGameRuleValue` (names = registry keys, which the `gamerule` command takes); `players_info` the online players.
- Caps: `chat_v1` (`chat.enabled`), `command_v1` (`commands.enabled` and, with `commands.require-token` (default true), a non-empty `auth.token`), `status_v1` (`status.enabled`); `welcome.chat`/`welcome.commands` for the granted ones.

### 3.10 Block entities (PROTOCOL.md 4.29)
- `BlockEntityStreamer` (a `Listener`; config section `block-entities`) runs every tick for sessions with `block_entities_v1`. ChunkSnapshots carry no block entities, so it reads them on the main thread with `Chunk#getTileEntities(predicate, false)`: only the block types with something to send (signs, banners, player heads, pots, spawners, trial spawners, beacons, campfires, shelves, vaults, conduits), and no snapshot copies. Reads are chunk by chunk within `budget-ms` (0.3 ms): first the chunks new to a region (nearest the centre first) and chunks touched by a block change in the region, a `SignChangeEvent` or a right click (`PlayerInteractEvent`), then a round robin. Chunks holding block entities that change by themselves (campfires, shelves, vaults, beacons, spawners, conduits) are read every `rescan-ticks` (40); the others every `STATIC_PASSES` (8) times as long, which picks up `/data` edits that fire no event.
- Entries are cached per world chunk as JSON strings, so several headsets and a glide reuse reads: a region change sends what the cache already knows and reads only the new chunks. `BlockEntityJson` (pure, unit-tested) builds the entries (leaving out defaults: empty signs, plain banners and pots, empty campfires and shelves, inactive conduits), packs positions like `BlockPos`, and diffs a chunk against what a session holds (`Session.blockEntitiesSent`): changed entries, `removed` positions, and the first message of a session or after a world change marked `reset`. Messages are built and serialised on the outbound thread (`sendCountingLater`), which counts the bytes.
- Player heads placed with only a name or UUID are completed off the main thread (`PlayerProfile#complete`, at most 4 at a time, cached per name or UUID); when one finishes, the head's chunk is read again on the next tick, which adds the skin and starts the lookups of heads that waited. A spawner's mob size comes from one `World#createEntity` per type, cached.
- The `BLOCK_ENTITIES` log line (every 30 s) gives ticks, chunks and entries read, main-thread ms (average and max), the slowest chunk read, bytes/s, sessions and cached chunks.

### 3.11 Using blocks, items and mobs (PROTOCOL.md "Using blocks and items", "Acting on mobs")
`InteractService` (a `Listener`; config section `interact`) owns `interact`, `item_registry`, `entity_op` and `entity_info`. `LinkServer` parses them on the websocket thread (`InteractMessages`, pure) and rate-limits there (`interact.max-per-second` shared by uses and mob actions, 20/s for `hold`/`drop`, spawn eggs per minute), then queues them for the main thread.
- **Decision (control audit option (a)):** curated Paper API calls, not a fake NMS player calling `ServerPlayerGameMode#useItemOn`. A fake player would give exact vanilla for every item, but needs paperweight-userdev (a new toolchain pin), a fake connection, advancement and stat files, fires `PlayerInteractEvent` with an offline player (protection plugins can break), and breaks on every update. The curated table covers what a builder-god uses, stays Paper-API-only apart from one guarded call, and is unit-tested on state strings.
- **`InteractRules`** (pure, `InteractRulesTest`): the empty-hand families by block id (doors, trapdoors, gates, levers, buttons, note blocks, repeaters, comparators, daylight detectors, bells, cakes, candle cakes, full composters, jukeboxes with a disc, lit candles and campfires; containers and signs as hooks) and the item uses (bone meal, fire, buckets, axe strip/scrape/unwax with the copper naming rules, honeycomb, hoe, shovel, shears, spawn eggs, the lightning wand), each an `Effect`: block changes as state strings at offsets from the clicked block, a sound key and pitch, and one extra (note, bell, eject, drop, primed TNT, bone meal, spawn, spawner type, lightning, neighbour update, release later). The Quest mirrors the empty-hand families in `World/UseRules.cs` to colour its outline; the server decides.
- **Applying:** every target cell is checked first (region, build height, border, loaded chunk; a door's other half only if it is there), then `setBlockData(data, true)` (physics on: a door's other half, dust and rails update as when a player clicks), `markDirty` for the diff, `World#playSound` with the vanilla key. Fire goes through `EditWorld.shapeFromNeighbours` and `isSupported`. Bone meal is `Block#applyBoneMeal` (vanilla `BoneMealItem`), the comparator's refresh and a button's release are the block's own `Block#tick()` (the release scheduled 20 or 30 ticks later, only if the button is still down), bells `Bell#ring`, jukeboxes `Jukebox#eject`, spawners `CreatureSpawner#setSpawnedType`, spawn eggs `spawnEntity(..., SPAWNER_EGG)`, TNT a `TNTPrimed` with an 80-tick fuse.
- **Neighbour bridge:** vanilla's lever and button also call `updateNeighborsAt` on the block they hang on (`LeverBlock#updateNeighbours`), so dust behind the wall sees the power; Paper has no API for neighbour updates at another position. `InteractService` calls `Level#updateNeighborsAt(BlockPos, Block)` reflectively (`CraftWorld#getHandle`, `CraftBlockData#getState().getBlock()`; checked with javap on the 26.3 server), resolved once, logged `INTERACT_NEIGHBOURS on`, and switched off with one warning if it ever throws (redstone behind the wall then updates with its next neighbour change).
- **Mobs:** `Server#getEntity(UUID)` (O(1)), the region plus `entities.margin`, the giant's tagged entities excluded. `attack` is generic damage plus vanilla's 0.4 knockback along the ray; `kill` uses `DamageType.GENERIC_KILL`; `hold` turns gravity and AI off and remembers what to restore (`Held`), restored on `drop`, the session's close, a 3 s silence (checked each tick), `/tabletop reload` and plugin disable. AI-off is saved with a mob, so a server crash mid-carry leaves it NoAI (rare; `/tabletop unfreeze-all` doesn't cover it). `freeze` is `Mob#setAware(false)`, saved with the mob, so frozen uuids go to `plugins/TabletopCraftAR/frozen.txt`; `/tabletop unfreeze-all` wakes the loaded ones and, through an `EntitiesLoadEvent` handler, the rest when their chunk loads.
- **Item registry:** built on start and reload: the usable items from the table whose family is on and whose item exists (`Registry.ITEM`), and the spawn egg (`ItemFactory#getSpawnEgg`) of every `EntityType#isSpawnable` type the world enables, minus `interact.deny-spawn` (18 usable, 86 eggs on 26.3, about 10–25 ms once).
- **Cost:** 0.2–3 ms of main thread per use (a first spawn about 10 ms with class loading), logged per use (`INTERACT`, `ENTITY`, and `..._DENIED`).

### 3.12 Operator tools: worlds, bookmarks, containers, signs (PROTOCOL.md "Operator tools")
`OperatorService` (config sections `marks` and `interact.containers`/`signs`/`sign-event`) owns `bookmark`, `container_query`, `container_edit`, `container_close` and `sign_edit`. `LinkServer` parses them on the websocket thread (`OperatorMessages`, pure) and rate-limits them there (bookmarks share the query bucket, containers and signs the interact bucket), then queues them for the main thread.
- **Worlds:** `welcome.worlds` and `region_info.worlds`/`spawn` come from `Bukkit.getWorlds()` (environment, min/max height, `getSpawnLocation`). Jumps and following are ordinary `region_request`s, so the server has nothing else to do for them; a request into another world is a full read (`RegionMerge` only copies within a world) and `region_changed.limits` carries its build height (§4.13). Following stays client-side: a server mode would have to move the shared region for every headset at the server's pace and couldn't ease with the figure the headset draws.
- **Bookmarks:** `Bookmarks` (pure: unique names ignoring case, sorted, capped at `marks.max`) in memory; every change is written to `bookmarks.yml` off the main thread (a YAML string built on the main thread, written to a temporary file and moved atomically; a newer write wins) and broadcast as `bookmarks` to every `marks_v1` session.
- **Containers:** a session has at most one view (`Watch`: position, the last message sent, the lid blocks). `Container#getInventory()` is the live inventory (a `DoubleChestInventory` for double chests, left half first), so views and edits go straight to the block entity: `setItem` marks it changed, which updates comparators. Every 4 ticks (and right after an edit) each open view is rebuilt and re-sent when its JSON differs; a view whose block is gone, left the region or another world is closed with a reason. `ContainerRules` (pure) holds the slot rules (vanilla `canPlaceItem` for furnaces, brewing stands and shulker boxes), sorting (merge by item id plus `ItemMeta#getAsComponentString`, then by id and size) and the default titles. Lids: `Lidded#open()` on the first view of a chest, barrel or shulker box (both halves of a double chest), `close()` when the last view of it ends; counted per block across sessions, and all closed on plugin stop. Cost: 0.04–0.25 ms of main thread per query or edit.
- **Signs:** `SignChangeEvent(block, null, lines, side)` first (when `interact.sign-event`): protection and logging plugins can change the lines or cancel; a cancel becomes "another plugin refused the sign change". The event has no player because the headset isn't one; Bukkit isolates a listener that throws. Then `SignSide#line`, `setColor`, `setGlowingText` and `Sign#update(true, false)`; waxed signs are refused. `markDirty` makes `BlockEntityStreamer` read the chunk again on the next tick, so `block_entities` carries the new text to every headset.
- **Undo:** with `power_v1`, `LinkServer` wraps `onContainerEdit` and `onSignEdit` in `PowerService.journalledTiles` (§3.13): the block entity before the edit (both halves of a double chest) goes into the session's undo journal.

### 3.13 Undo, box edits and brushes (PROTOCOL.md "Undo, box edits and brushes")
`PowerService` (config section `edit`: `power`, `undo-depth`, `box-max-blocks`, `box-budget-ms`, `brush-...`) owns `undo`, `redo`, `box_edit`, `brush`, `history` and `box_progress` for sessions granted `power_v1` (granted at hello after the caps loop, since it needs `edit_v1`). `LinkServer` parses them (`PowerMessages`, pure) and rate-limits `undo`/`redo`/`box_edit` there; brush strokes are limited by blocks per second on the main thread.
- **Journal** (`UndoJournal<S, T>`, pure and generic, `UndoJournalTest`; Paper `BlockData` and `BlockState` snapshots at run time): per session, a deque of groups (cells keyed by packed position, first "before" and latest "after" kept per cell), a redo deque cleared by any new group, bounded by `undo-depth` blocks (oldest groups dropped, the newest always kept whole) and `undo-tile-entities` snapshots (oldest dropped first). Groups remember their world.
- **Single edits** are journalled without touching `onBlockEdit` or `InteractService`: `LinkServer` wraps the queued call in `PowerService.journalled`, which reads the cells around the target (3×3×3; 7×14×7 for bone meal) and snapshots their block entities (`Block#getState()`, only for materials whose `createBlockState()` is a `TileState`, cached), runs the edit, and records every cell whose `BlockData` changed. That catches both halves of doors and beds, waterlogging and the neighbours whose connections changed, for 27 block reads before and after (686 for bone meal). `container_edit` and `sign_edit` go through `journalledTiles` the same way: the clicked block entity and a double chest's other half, recorded when the snapshot's own inventory (`Container#getSnapshotInventory`: a placed state's `getInventory()` is the live one) or the sign's sides differ afterwards.
- **Jobs** (`BoxJob`, `UndoJob`, `BrushJob`): one per session at a time (brush strokes queue up to 3), stepped from `TabletopPlugin.tick()` right after the queue is drained, all sessions together within `box-budget-ms` (round robin; the clock is checked every 16 cells). A job writes with `setBlockData(data, false)` (Paper sets the state with `UPDATE_CLIENTS | UPDATE_KNOWN_SHAPE | UPDATE_SKIP_ON_PLACE`, javap on the 26.3 server: no neighbour reactions or shape updates, light follows in the chunk; block entity side effects still run, so a block with an inventory is emptied first, its own half of a double chest only, rather than spilling what the journal keeps; vanilla `/fill` skips them with `UPDATE_SKIP_BLOCK_ENTITY_SIDEEFFECTS`), records before/after, marks one cell per touched chunk dirty per tick (`markDirty`: the normal diff sends `block_update` or, over 4096 changes, the changed sections), then runs a **fix-up pass** over the changed cells: connecting blocks among them and their neighbours inside the region (`MultipleFacing`, `Wall`, `Stairs`, `Rail`, `RedstoneWire`, `Snowable`, `Gate`, `Leaves`) get `EditWorld.shapeFromNeighbours` (vanilla `Block.updateFromNeighbourShapes`), and with `edit.physics` each changed cell gets vanilla's `Level#updateNeighborsAt` through the same guarded reflective bridge as levers (`POWER_NEIGHBOURS on`), as `/fill` does. Undo restores a cell from its block entity snapshot with `BlockState#update(true, false)` (state and contents in one go). The box planner (`BoxPlan`: cell order bottom up, which cells each op touches, the clone's quarter turns, `BoxPlanTest`) and brush shapes and smoothing (`BrushShape`) are pure. Changed positions live in a primitive `LongSet` (no boxing).
- **Cost** (`tools/power_check.py`, Paper 26.3 on a desktop core, JIT warm): a 32768-block fill in 21 ticks, 44 ms of main thread in all (fix-up 21 ms), at most 3.8 ms in one tick (one tick over 1.5× the budget, a GC pause); its undo in 18 ticks, 34 ms. Small groups undo in under 0.5 ms. Each job is logged (`POWER session=... fill ... main thread ... ms ... max ... ms in a tick`), refusals as `POWER_DENIED`.

### 3.14 Sound and asset delivery (PROTOCOL.md "Sound", "Asset delivery")
- `SoundGroups` reads every block's `BlockData#getSoundGroup` once per start (1283 blocks in 129 groups on 26.3, 8 ms) and sends it as `sound_groups` to `sound_v1` sessions after the registries. `ActionListener` adds `sound` and `sound_stop` actions to the tick's `ActionBatch` (only sessions with `sound_v1` get them) from `NotePlayEvent`, `BellRingEvent`, `GenericGameEvent` (container open and close, jukebox play and stop), explosions, ignition, buckets and fertilizing; `InteractService` adds the sound it plays for the headset's own use. Everything else the headset infers (PROTOCOL.md "Sound", client guidance), so a busy server sends no per-footstep traffic.
- `AssetService` (config `assets`, off by default): on start it hashes `pack.zip`, `entity_models.json` and `sounds.zip` from `assets.dir` on its own thread; `grant` checks the token is set and the address is on the LAN; `offer` goes out after welcome (or when hashing finishes); `asset_get` is checked on the WebSocket thread and scheduled on the asset thread at the session's next free slot (`assets.max-mb-per-second`), which reads the range with a `FileChannel` and sends one binary frame. A file that changed on disk is hashed again and offered anew.

## 4. Quest app

- Base: copy the HUD repo's Unity 6000.0.84f1 + Meta XR Core/MRUK setup and its Project Setup Tool flow. Built-in render pipeline. OpenXR or the Oculus XR plugin, as the HUD repo did. Android IL2CPP ARM64.
- Scene: an `OVRCameraRig` with passthrough enabled (`OVRPassthroughLayer`, underlay), the MRUK prefab with **Load Scene on Startup**, and the `USE_SCENE` permission.
- Placement: after `MRUK.Instance.SceneLoadedEvent`, find the anchors labeled `TABLE`. Pick the nearest to the head and use `PlaneRect` (or the top of `VolumeBounds`). `TabletopAnchor` goes to the plane's center, rotated so its local +Y is the table normal. Fallbacks: no scene or no table → the user places the world with a controller raycast against `EnvironmentRaycastManager` or the floor at 0.75 m. A grip on both controllers moves, rotates or scales it. [comfort] A held for 0.5 s re-places it at the right controller; the pose is saved relative to the TABLE anchor (its UUID, centre and in-plane yaw) in `prefs.json` and restored when the scene has that table again; a scene that loads after a manual placement doesn't move it.
- Rendering:
  - **Mesher:** a greedy mesher per 16x16x16 sub-volume (so `block_update` only rebuilds one sub-mesh). It culls faces against neighbors, and faces only merge when they have the same texture, tint and texture rotation. Greedy UVs are in block units from the section-local corner, in vanilla's per-face orientation (grass fringe up on every side), so merged quads tile exactly like single blocks. A second whole face on a side (the grass block's biome-tinted `grass_block_side_overlay`) rides along as `FaceKey.Overlay` and is emitted as a second quad on exactly the base quad's corners, right after it in the same submesh with the same diagonal, so it wins the LEqual depth test without z-fighting and without a shader or vertex-layout change. Faces between two leaves blocks are drawn like vanilla's default `cutoutLeaves` (`GreedyMesher.LeavesInner`, `tabletop.json` `leaves_inner`). Only full cubes and fluids go through the greedy path. Everything else is drawn from its block model (below). Without a pack there are no models, and non-cube states fall back to placeholders from a name-based rules table (a cross quad or a half block). 32x64x32 makes at most 8 sub-meshes. [mesh] **Per-section fast paths** (TESTING.md "Faster meshing"): the greedy pass copies the section and a one-cell border into padded arrays once (palette id and `BlockShape` per cell, from `WorldModel.ShapeOf`'s per-palette table) and looks up face keys and the leaves flag once per palette id per section; it used to make two string-keyed dictionary lookups per cell and direction (about 50,000 per section, most of the cost of an all-air or all-stone section). A section without cubes returns at once. Smooth lighting reads light and shape flags from a per-section `ShadeCache` (the section plus a two-cell border, filled when its first face is lit) through the same code path as the world (`BlockShading.Corners<T>` over a struct cell reader). `BuildSpecials` and model culling take shapes from the palette id, and the fluid pass skips the border when the section has no visible fluid. The output is identical, vertex for vertex (`Tests~ --profile-mesh --hash` on real snapshots).
  - **Block models** (`World/BlockModelBaker.cs`, `World/BlockModels.cs`, `World/ResourcePackAtlas.Models.cs`): with a pack, each palette state's model is baked on the main thread the first time the renderer prewarms it (`Atlas.Face`). The baker handles blockstate `variants` (property match, `x`/`y` rotation, `uvlock`; weighted random lists are baked per combination and picked per block like vanilla, below) and `multipart` (every part whose `when` matches, including `OR`/`AND` and `a|b`), the model `parent` chain with `#texture` variables (26.x `{"sprite", "force_translucent"}` objects too), and elements with `from`/`to`, per-face `uv` (default from the bounds), `rotation`, `cullface` and `tintindex`. Element rotation can be axis/angle/origin/`rescale` or 26.x `x`/`y`/`z` angles. The result is a list of quads in block units with UVs inside the texture layer (0..1, so no shader change), plus a 16x16 coverage mask per side. Classification (`BlockRules.SetShape`) then follows the model, not the name. Six whole boundary faces with cullfaces (or an opaque shell with hidden inner faces, like powder snow) make a full cube. It stays greedy, with its x/y-rotated textures and a `FaceKey.UvMap` for rotated faces such as sideways logs. Cut-out or translucent cubes (copper grates, frosted ice) become `TransparentCube` so they don't hide neighbours. Anything else becomes `BlockShape.Model`, and `BuildSpecials` emits its quads on the worker threads (`BlockModelMesher`). A face with a cullface is dropped when the neighbour is an opaque cube, when the neighbour's model covers that side (snow layers, slabs and stairs side by side), or, for translucent faces, when the neighbour is the same block (joined glass panes). Opaque and cut-out faces go to the alpha-tested submesh; faces with partially transparent textures or `force_translucent` go to the blended one. Inside-out helper elements (`from > to`) are kept only for see-through textures (spawner cages). Blocks that vanilla draws entirely in code (chests, banners, heads, shulker boxes, decorated pots, conduits, end portals and gateways, copper golem statues, the bell's body) have no model geometry. The app sets `BlockEntityBoxes` off and leaves them to `BlockEntityRenderer` (below); with it on (the default, used by the tools and `Tests~ --measure`) they get simple boxes from their particle texture (banners use the matching wool, heads a flat colour), and bells a body under their frame. `OnlyEntityBoxes` bakes nothing but those boxes, for the one-block hand preview and placement ghost (`BlockEntityPreview`). Redstone dust and stems take their state colour, not the biome tint, and a `tintindex` only counts on the 28 blocks vanilla's `BlockColors` tints (pink petals and wildflowers only on index 1, their stems); everything else draws untinted (cherry and pale oak leaves, bamboo...). 26.x element `light_emission` (eyeblossoms, firefly bushes) raises a face's sky and block light; models with `"ambientocclusion": false` (doors, rails, crops...) are lit flat (one light per face, no AO; `BakedModel.Shade`), and the emissive magma block and active sculk sensors full bright. Face textures are slots with or without `#` (the heavy core's `"all"`).
  - **Vanilla's randomness** (`BlockRandom`, `RandomUv` in `World/BlockModelBaker.cs`/`BlockModels.cs`, from the 26.3 bytecode): offset plants (flowers, grass, ferns, bamboo, roots, dripstone...) move by `Mth.getSeed(x, 0, z)` bits like `BlockBehaviour.Properties.offsetType`; weighted blockstate lists pick per block exactly like `ModelBlockRenderer` (the java.util.Random LCG seeded with `Mth.getSeed(pos)`; `WeightedVariants` draws `nextInt(total)`, `MultiPartModel` one long reseeding every part), so lily pads, turtle eggs, fire and chorus plants vary as in the Java client. Greedy cubes with random rotations (stone, dirt, grass tops, sand, netherrack, deepslate...) keep their merging: each side gets a table of UV codes (how each variant's UVs differ from variant 0's), the mesher encodes it in `uv.z` (layer + 4096 × table), and `Shaders/TabletopBlocks.cginc` turns the in-block texture coordinate per block cell from a hash of the world block (each batch renderer carries its world origin in `_TabletopCell0`), with gradients from the continuous UV. That pick is a stable hash, not the Java client's exact choice (64-bit maths per pixel); the cut caps stay unrotated.
  - **Moving pistons** (`World/PistonGhosts.cs`): `moving_piston` bakes to nothing, so `WorldModel` keeps each `block_update`'s old states of the changed cells and works out what a moving cell draws until its final state: the head in front of a base that just extended, a pushed block in the cell it moves into, a sticky piston's pulled block in the head cell, a retracting base its extended look. Blocks jump instead of sliding (no 2-tick animation), but nothing blinks. Workers only read baked data. A worker that meets a palette entry the main thread hasn't prewarmed yet (a race with `block_update`) gets an uncached flat colour, and that section is meshed again after the next prewarm.
  - **Atlas:** runtime-built from a **user-supplied** resource-pack zip (or the user's own `client.jar`) copied to the headset's app storage (`/sdcard/Android/data/<pkg>/files/pack.zip`). Read `assets/minecraft/blockstates/*.json` → `models/block/*.json` (resolve the `parent` chains and `textures` variables) → PNGs. Greedy-merged faces need tiling, so it is a `Texture2DArray` (one 16x16 layer per texture) with UVs in block units and wrap/repeat instead of a 2D atlas, which also avoids atlas bleeding on merged quads. Every layer has a mip chain built like 26.3's `MipmapGenerator` (`World/TextureMips.cs`: linear-light 2x2 means; textures with transparent pixels are solidified and keep level 0's alpha coverage at the shader cutoff, so flowers and glass don't vanish in the distance), sampled trilinear far away while the block shaders sample texel centres up close (vanilla's nearest magnification); a 16 px layer is 1,364 bytes instead of 1,024. `tabletop.json` `mipmaps: false` keeps the single point-sampled level. Without a pack, the app colors faces from a built-in flat color table, so it works with zero Mojang assets.
  - **Fluids** (`FluidMesher`, engine-free, on the meshing workers, run last in `BuildSpecials`): fluids no longer take the placeholder or greedy-cube path. A cell holds water if it is water, has `waterlogged=true`, or is kelp, kelp_plant, seagrass, tall_seagrass or bubble_column. The fluid is drawn in addition to the block. Faces between cells that hold the same fluid are culled, as are faces hidden by a full opaque face of the cell's own block or of the neighbour (`FluidRules.FullFaces`). Surface heights follow vanilla `LiquidBlockRenderer`. Flat faces are greedy-merged, and UVs come from positions so merged or lowered faces tile instead of stretching. Water goes last into the transparent submesh, so it blends over the plants inside it; lava goes into the opaque submesh. Fluids use the faces of `minecraft:water`/`minecraft:lava`, which the renderer prewarms on the main thread. `FluidMesher.WaterColor` gives the per-biome water colour (BlockShading).
  - **Animated textures** (`TextureAnimation` parses `.png.mcmeta`; `ResourcePackAtlas.Animation.cs`): an animated texture keeps one atlas layer, so meshes and shaders don't change. All its frames go into a second `Texture2DArray` (the frame store). `Animate()` runs each frame from the renderer and follows game ticks (20/s). When a texture's frame changes, it copies that frame into the atlas layer with `Graphics.CopyTexture` (GPU to GPU, 1 KB at 16 px; every mip level, each frame has its own chain). Interpolated animations are blended on the CPU into a one-layer staging array and copied the same way. The atlas is only re-uploaded when new textures arrive.
  - **Eye in a fluid** (`World/EyeMedium.cs` engine-free and tested; `World/EyeEffects.cs` on the headset).
    - **Medium.** Each frame the centre eye is mapped into block space (`Blocks.InverseTransformPoint`, Z mirrored back to the Minecraft frame) and classified as air, water, lava, powder snow or solid. Like vanilla `Camera.getFluidInCamera`, only the eye position counts:
      - Water and lava fill a cell up to its fluid height: 1 under more of the same fluid, else amount/9. That makes a source 8/9 high and flowing water lower. The height is the cell's own, not the averaged corners of the drawn surface.
      - Waterlogged blocks, kelp, seagrass and bubble columns count as water.
      - Exactly at the surface is air.
      - An opaque cube, or the solid half of a slab, is solid. Powder snow fills its whole cell.
      - Outside the region is air.
    - **Filter.** `EyeMediumFilter` stops flicker at a surface: a new medium must hold for 50 ms, and leaving one needs the eye 4 mm past its edge (clamped to 0.05–1 block). Looks fade in and out over 0.2 s.
    - **Fog.** The block and player shaders apply distance fog from the centre eye (`Shaders/TabletopFog.cginc`, three globals, no keywords; strength 0 = off). Distances are vanilla's in blocks × the block size in metres:
      - Water fogs toward the biome water colour at the eye (`BiomeTints`, else 0x3F76E4). It runs from 8 blocks behind the eye to 96 × max(0.25, water vision) blocks, so visibility goes from 24 to 96 blocks over 30 s as vanilla's "eyes adjust". The colour also brightens as vision grows.
      - Lava: (0.6, 0.1, 0) from 0.25 to 1 block.
      - Powder snow: 0 to 2 blocks.
      - Solid: dark fog within 1.5 blocks at 90%.
    - **Passthrough tint.** `Shaders/EyeOverlay.shader` (shipped as `Resources/TabletopEyeOverlay.mat`) draws a box around the head first, in the Background queue, with ZTest Always and premultiplied alpha. Blocks draw over it with their own fog, so it only tints what is behind the miniature. Opacity: water 45% of its fog colour, lava 80% orange, powder snow 70% white, solid 70% black. That is dim, never a blackout. A full-screen post effect would cost a resolve on the Quest and would double-tint the blocks.
    - **Water seen from inside.** `FluidMesher` gives every water face a reversed copy with its own vertices (so the outside face keeps its shading normal) in `MeshData.WaterBack`. That list is a third submesh. `TabletopRenderer.Underwater` adds a third material to every section only while the eye is in water: a renderer draws only as many submeshes as it has materials. So the surface is visible from below, and the region's cut walls look like an aquarium from inside. From outside nothing is drawn twice and nothing z-fights. Lava has no inside faces.
    - **Edge cases decided:**
      - A region top that cuts through deep water is a surface at 8/9 for both drawing and the eye: a cross-section look.
      - Falling water (waterfalls) is full height under more water, and its sides have inside faces.
      - Ice over water leaves the vanilla 1/9 air gap. Ice and glass are air to the eye.
      - Lava next to water: each cell is its own medium.
      - Region edges: outside is air, even next to a tank wall.
      - Half the view under water: the eye position decides, as in vanilla.
      - Sorting: with a pack, kelp and seagrass are cutout textures in the opaque, depth-writing submesh, so they sort correctly against the surface from below. Transparent cubes (glass, leaves) and the no-pack placeholder crosses are in the transparent list and can show behind the inside faces.
      - With the head inside a stair model the medium is the cell's fluid or air; only cubes and slab halves are solid.
      - Nav's visible window:
        - An eye outside the clip box (`_TabletopClip`) is in air, even if the loaded region has water there.
        - The window's cut sides (`ClipCaps`) cut any water-holding cell as water (`CapMesher.CapState`), so kelp and waterlogged cells leave no holes.
        - Water cuts get inside copies, and `ClipCaps.Underwater` toggles them like the renderer: the aquarium wall from inside is the window side.
        - Known gap: caps are full squares, so at the waterline the cut shows a 1/9-block lip above the 8/9 surface.
  - **Vertex colours: biome tint × light × AO** (`World/BlockShading.cs`, `World/BiomeColors.cs`; the contract is at the top of `GreedyMesher.cs`). The atlas only decides *which* tint a face takes (`FaceKey.Tint`: grass, foliage, dry foliage, water, from the model's `tintindex` and vanilla's per-block rules; spruce/birch leaves, lily pads, stems and redstone get fixed colours). The mesher resolves the colour per block from the server's 4x4x4 biomes: override colours or the pack's `colormap/{grass,foliage,dry_foliage}.png` at the biome's temperature/downfall, swamp/mangrove grass from vanilla's seed-2345 simplex noise, dark-forest grass darkening, per-biome water, blended over 5x5 columns like vanilla's default biome blend. Light follows vanilla's smooth lighting: per vertex, the 4 cells in front of the face are averaged (`smoothBlend`) and looked up in the 26.x lightmap at noon, times AO from the 3 neighbouring occluders. For AR the lightmap uses vanilla's "Bright" setting and is rescaled so light level 0 shows at 0.2 (`min_light`) instead of near black; everything outside the region counts as open sky-lit air, so the cut sides read like daylight cross-sections and caves cut by the edge brighten towards the cut. Model quads (`BlockModelMesher`) use the same helper: axis-aligned faces get the smooth light/AO of their block face (bilinear for partial faces, like vanilla's partial-face weights), rotated faces (crosses, 22.5°/45° elements) the block's own light, and tinted faces the biome colour. Fluids are lit like vanilla `LiquidBlockRenderer`: one light per face, the max of the cell and the cell above, no AO, and per-biome water through `FluidMesher.WaterColor`. Faces merge only when their 4 corner colours are equal and constant along the merge direction, which costs about +24-38% faces in total on real terrain with the pack's models and water (greedy faces +55-66%; model and fluid faces barely change; TESTING.md "Lighting with models and water"); `smooth_lighting: false` in `tabletop.json` keeps one light value per face (+4-17%). `AreaMath.LightFactor` (x1.35 smooth, x1.15 flat) scales the area-setup estimate to match. The shaders multiply vanilla's per-direction face shade (top 1.0, bottom 0.5, north/south 0.8, east/west 0.6) and leave diagonal faces (cross plants) unshaded, as vanilla does. Without light/biome data (an older server) colours are exactly the old fixed tints, unlit.
- Players: Minecraft-style figures (`PlayerMarkers` → `PlayerFigure`): six boxes with the game's model sizes and skin UV layout including the second layer (`PlayerModel`, from the game's `PlayerModel`/`ModelPart.Cube`), 1 px = 1/16 block. Positions, yaw and pitch ease toward the 10 Hz samples in world coordinates; `PlayerAnimation` (engine-free) adds limb swing from horizontal speed, idle arm bob, body yaw that lags the head (max 50°) and turns toward the walking direction, and the sneak pose. Skins (`PlayerSkins`): the `skin` URL (textures.minecraft.net only, fetched over https with `UnityWebRequestTexture`, cached per URL, legacy 64x32 skins converted as the game does), else the default skin the game picks for that UUID from the user's `pack.zip`, else a plain-colour skin. Shader `TabletopCraft/PlayerSkin` (unlit, alpha test, no culling, the game's fixed two-light entity shading), shipped through `Resources/TabletopPlayer.mat`. - Moving around (PROTOCOL.md 4.17-4.18, QUEST_SETUP.md Part H): the region has a view margin; `XR/NavController` + the engine-free `World/NavState` slide the visible window inside it (left stick) and request the region shifted by whole 16-block sections when the view is 4 blocks past the region's centre. While the view moves steadily along an axis (8 blocks one way without stopping), `NavState` shifts the region **ahead**: as many whole sections as fit while 16 blocks stay loaded behind the window, so most of the margin is runway. A shift back needs the view to come back past where the last shift left it plus 3 blocks (hysteresis), so stopping, turning round or wiggling never ping-pongs; vertical lookahead stops at the build height. The speed cap is the runway one round trip sustains (`NavState.Runway`: 32 blocks at a 48 margin, 18 at 32, 12 at 16) over 1.3 × the glide latency (request until the region is applied; resizes don't count), and `MeshCap`.
  - [nav] **Lazy margin** (`World/MeshScope.cs`): the margin is runway, not something to look at, so only sections near the window are meshed: the window plus 8 blocks, plus 0.6 s of travel ahead in the direction of motion (`Active`); meshes further than 16 blocks beyond that are dropped (`Keep`) and meshed again when the window comes back. Sections outside stay dirty in `WorldModel`; a shift's new sections arrive deep in the margin and cost no meshing until the window approaches. Meshing order: sections on screen first, then the ones ahead of the motion (`MeshScope.Score`). Each worker job meshes several sections in a row: [mesh] about 1.5 frames of work at the measured worker time per section (`MeshWorkMeter`, `MeshScope.SectionsPerJob`: at least `mesh_sections_per_job`, default 4, at most 64), since jobs are handed out once per frame (one section per job capped meshing at 3 sections per frame, fixed jobs of 4 at 12 per frame, 864/s at 72 Hz, however cheap a section was). `tabletop.json` `mesh_workers` sets the number of meshing workers (default 3: the Quest 3 gives an app about three cores, and Unity's main and render threads use two). The renderer measures its throughput while every worker is busy (`MeshRateMeter`), and `MeshScope.MeshSpeedCap` turns it into the fastest pan at which meshing keeps up: 65% of the rate × 16 / the sections in one slice of the active box. `NavController` logs a `GLIDE` line every 5 s of stick time.

Faces take the block's own face keys (texture layer, random-rotation table; no overlay), the biome tint and the flat light of the cell in front (`BlockShading.Flat`, with its light code for the time of day), and sit 0.03 blocks inside the real surface, so where detail has arrived it wins the depth test. - **Batching** (`World/SectionBatches.cs`, `World/TabletopRenderer.cs`; PLAN.md roadmap item 7): sections are meshed one by one as before, but no longer drawn one by one (1,223 non-empty sections and about 2,000 draw calls for a 256-wide window with its margin).
  - The meshing worker turns each section's `MeshData` into an immutable `SectionMesh`: Unity space (Z mirrored, winding flipped), relative to the section corner, with normals computed there the way `Mesh.RecalculateNormals` does (normalised sum of the unit triangle normals; zero where a double-sided quad cancels), packed as 32-byte vertices (float3 position, snorm8 normal, colour, float3 uv). The renderer keeps one per non-empty section.
  - Sections are grouped into **batches** of `BatchRules.Columns`² section columns (default 2×2, 32×32 blocks) over the region's full height, one GameObject/renderer per batch with the same three submeshes (opaque, transparent, water seen from inside) and materials as before. Batch keys are aligned to **world** section coordinates (`BatchLayout`), so when the region shifts or resizes by whole sections a batch keeps its key and its mesh and only moves. Its y offsets are anchored to the world section index it was built against, so a vertical shift doesn't move a kept mesh either.
  - When a section's mesh changes (new terrain, `block_update`, light, an edit) its batch is marked dirty. A dirty batch is reassembled on a worker (`BatchData.Assemble`: concatenation with offsets, pooled arrays) once none of its sections is still being meshed, or after 0.4 s so a big area fills in progressively, and uploaded on the main thread with the advanced Mesh API (`SetVertexBufferData`/`SetIndexBufferData`, bounds from the assembly) within the same 3 ms per-frame budget (at least one upload per frame). After a re-key (`BatchRules.AfterRekey`) the batches that lost sections are rebuilt and the ones left without sections destroyed; staging (a region elsewhere) keeps the old batches on screen as before. Frustum culling is per batch. [mesh] While gliding: a section dropped outside `KeepScope` doesn't re-upload its batch (its old geometry there is at least 24 blocks outside the window, where the clip box hides it); the batch goes on a trail list and is rebuilt when it has no meshes left (an empty mesh, nothing to upload), when something else dirties it, after 4 s, or when meshing is idle and the view stands still. A batch entirely off screen (`BatchRules.OffScreen`) also waits, at most `BatchMaxWait`, for its dirty sections in `KeepScope`, so a batch ahead of a glide is uploaded once with both its columns instead of once per column. At 256 wide a glide re-uploads 0.28-0.32 MB per block of travel instead of 0.34-0.43 MB.
  - Batch size by measurement (TESTING.md "Area size presets and batching"): 2×2 gives 36 renderers / 72 draw calls at a 128-wide window and 100 / 200 at 256, with batches under about 90k vertices (3 MB), so an edit re-uploads about 1.3 MB. 4×4 halves the draw calls again but re-uploads 5–9 MB per edit. `tabletop.json` `batch_columns` overrides it. Transparent faces now sort per batch instead of per section.

- Using blocks, items and mobs (QUEST_SETUP.md Part M; `XR/BlockEditMode.cs`, `XR/EntityCard.cs`, engine-free `World/UseRules.cs`, `World/EntityRaycast.cs`, `World/EntityCardModel.cs`, `Net/InteractProtocol.cs`): each frame `BlockEditMode` casts the right ray twice in block space: the DDA (`BlockRaycast`, through fluid sources only while the empty bucket is selected) and a slab test against the boxes of the mobs and players as they are drawn (`EntityRenderer.Targets`, `PlayerMarkers.Targets`: eased positions, at least half a block; players 0.6 × 1.8). The nearer wins. `UseRules.Decide` turns that, the target block's state, the selection, the left grip and tabletop.json `left_trigger` into the left trigger's action (mob, block use, container or sign hook, item, place), which also colours the outline. Uses are sent as `interact`/`entity_op` and never guessed locally. The right grip carries a mob: after 0.25 s (so a both-grips drag never lifts it) `hold` messages at about 10 Hz put it a block above the drop point, drawn as a translucent box; letting go sends `drop`. The block menu shows `item_registry` as Use and Eggs tabs of `BlockEntry`s whose state is `item:<id>`, so the hotbar, prefs and icons treat items like blocks. `entity_info` opens `EntityCard`, a small panel above the mob drawn like the operator panel, whose buttons send `entity_op`. Containers and signs call `OnContainerUse`/`OnSignUse`, which open the container view and the sign editor in the operator panel (next bullet).
- Operator tools (QUEST_SETUP.md Part N; engine-free `World/FollowState.cs` (`Jumps`, `JumpFocus`, `FollowState`), `World/MarksModel.cs`, `World/ContainerModel.cs`, `World/SignEditorModel.cs`, `Net/OperatorProtocol.cs`; `XR/NavController.cs`, `XR/OperatorPanel.cs`): **jumps** are `Jumps.Plan`: the current x/z size and margins, the height shrunk to the target world's build height (welcome.worlds), centred on the target, the origin moved by whole sections in the same world so the server reads incrementally; they go through `NavState.TryIssue` (kind `jump`, left out of the glide latency) and `JumpFocus` puts the view on the target when the region with that origin is applied (`NavController.OnSnapshot`). **Following** (`FollowState`) runs in `NavController.Update` when the stick is idle: the followed player's eased figure (`PlayerMarkers.TryShown`) or, when it isn't on the table, `region_query{player}` (sent with `SendTracked`; its `region_info` or error comes back by `ref_seq` before area setup sees it) gives the target; the view eases after it (exponential, dead zone, vertical band) through the same `NavState.Move` as the stick, and jumps when the target is 16 blocks beyond the loaded region or in another world. A stick glide, area setup, Reset view or a Marks jump stop it (a toast says why). The **Marks tab** and the **container view** and **sign editor** live in `OperatorPanelModel` (a sixth tab, and `PanelMode.Container`/`Sign` replacing the tab's content; a tab click leaves the mode), with their state in `MarksModel`, `ContainerModel` and `SignEditorModel`; messages they want sent go through the model's `Outbox`, which `OperatorPanel` flushes each frame (a closed view always sends `container_close`). Slot icons are drawn from the block menu's `BlockIconAtlas` (blocks by their registry state, items as `item:<id>`) on a third panel mesh at queue 3011; dye swatches use the pack's dye colours from `entity_models.json` when present.
- Power tools (QUEST_SETUP.md Part O; `XR/PowerToolMode.cs`, engine-free `World/PowerTools.cs`, `Net/PowerProtocol.cs`): `BlockEditMode` starts an edit group (`EditGroups`) on every trigger press and stamps it on `block_edit` and `interact` through `BlockEditor.Group`; B goes through `TapHoldButton` (a tap on release picks, or with a tool on picks Replace's filter; 0.6 s held undoes, then every 0.4 s). `PowerTools` holds the tool mode, the wand's corners (world coordinates), the filter, paste mode and its turns, the brush (form, op, radius, a client-side token bucket under `brush_blocks_per_second`), `history` and the last `box_progress`, and turns Tools tab buttons into `undo`/`redo`/`box_edit`/`brush` messages or a local refusal; jobs go out with `LinkClient.SendTracked` so their `box_progress` and `error` match by `ref_seq` (one job at a time, like the server). `PowerToolMode` owns the left trigger while a tool is on (`BlockEditMode.LeftTaken`), sets corners or pastes on a press, sends strokes while held, and draws three `LineRenderer` boxes in block space cut to the visible window (the wand's cyan box, the paste's orange copy at the aimed face, the brush's reach). The Tools tab is part of `BlockMenuModel` (`MenuPart.Tool`, buttons from `PowerTools.Rows`, five status lines).
- Sound (QUEST_SETUP.md Part E step 4 and Part P; `World/TabletopSound.cs`, engine-free `World/SoundDefs.cs`, `SoundRules.cs`, `SoundDirector.cs`, `SoundMixer.cs`, `SoundPack.cs`): `TabletopApp` hands `SoundDirector` every `block_update` (before it is applied, so old and new states are known), `actions`, `entities`, `player_positions`, `chat` and the own edits (`BlockEditor.Edited`); the director turns them into requests the way the game client would (state-change sounds, a step per 1/0.6 blocks walked, the 80-tick ambient clock, the 4-tick digging hit, rain and the fluid/fire ambience sampled over the visible window at 20 Hz, a one-second dedupe per block and sound). `TabletopSound` picks a variant (`SoundDefs`, vanilla weights), computes the game's linear fall-off with the distance scaled by block size × `sound_range`, lets `SoundMixer` give it one of 24 voices (priority classes, per-event and per-class caps, stealing the least important), and plays it on an AudioSource under RegionRoot. Clips: copied out of `sounds.zip` into `temporaryCachePath/sounds_<size>_<date>/` on a worker, decoded by `UnityWebRequestMultimedia` (OGG Vorbis, `file://`), about 300 kept (LRU); a request waits up to 0.4 s for its clip. The scene has no AudioListener, so one goes on the head.
- Asset download (QUEST_SETUP.md Part P; engine-free `World/AssetSync.cs`, `Net/AssetProtocol.cs`): `LinkClient` gathers binary frames and hands them to `AssetSync.OnBinary` on the receive thread, which writes them into `<name>.part`; `Pump` (main thread) sends up to 4 `asset_get` at a time and reports finished files; hashing (the local copies, cached in `assets_hashes.json`, and each finished download) runs on a worker. `TabletopApp` reloads sounds and entity models in place and reloads the scene for a new `pack.zip`.
- Network: `LinkClient` on a background task with `ClientWebSocket`, JSON parsed there into an `InboundQueue` drained on the main thread (bounded at 4096 messages by not reading; a full snapshot drops the queued snapshots and block updates it supersedes), a 30 Hz pose sender from `Update` (head = center eye, hands = controller anchors or hand-tracking wrists), and auto-reconnect with backoff. `LinkClient` pings every 2 s itself (RTT, cleared while down), aborts a link silent for 6 s, gives up connecting after 5 s, and stops retrying on close 4001/4003. Hold the Wi-Fi low-latency lock as in the HUD repo.
- Session ([comfort], QUEST_SETUP.md Part D): `TabletopApp` stops the link while the headset is off (`OVRManager.HMDUnmounted`, `OnApplicationPause`; `avatar_config enabled:false` + `bye`) and starts a new one when it's back. `World/SessionState.cs` (engine-free) decides the setup card (`XR/SetupCardView`), the offline badge and the north marker (`XR/TableMarkers`), hides players and entities after 1.5 s offline, and drives the `Loading area N %` toast. `World/AppPrefs.cs` is `prefs.json` (debounced writes, the tabletop.json-vs-prefs rule, the table pose relative to the MRUK table). `Net/LanDiscovery.cs` is the Server field's search (PROTOCOL.md §7: UDP probe, /24 TCP fallback); `World/KeyboardModel.cs` the reusable panel keyboard.

## 5. Networking/latency notes (from ironman-quest3-hud)
- LAN unicast only (plus the discovery probe, a UDP broadcast to 8765). Router AP isolation must be off, and the plugin port (8765/tcp, and 8765/udp for discovery) has to be open on the server PC's firewall.
- Measured in the literature: about 63–106 ms end to end PC↔Quest over TCP. That's fine for a giant whose motion is interpolated over 2 ticks (100 ms).
- Quest Wi-Fi can deliver traffic in bursts; the server's latest-pose-per-tick slot absorbs that.
- The protocol's `ping`/`pong` gives RTT; the Quest logs it to logcat (`adb logcat -s Unity`).

## 6. Security (LAN v1, public later)
Shared token in `hello`, bind address configurable, per-connection rate limit on poses. Block editing from the headset (§3.7) is on by default for LAN use, limited to the session's region and 20 edits/s; `edit.require-token: true` restricts it to headsets holding `auth.token`, and `edit.enabled: false` turns it off. Chat from the headset (§3.9) is a server message with a fixed `[Giant]` prefix and a sanitised name, so it can't pass for a player. Server commands from the headset run with operator rights, so they need `auth.token` by default (`commands.require-token`); a deny list (`stop`, `op`, `ban`, `whitelist`, `reload`... checked through aliases, namespaces and `execute … run`), an optional allow list, 2 commands/s per headset, 256 characters, a log line per command and the `[Tabletop: /line]` echo to ops limit and expose them. The token and the commands travel in clear over `ws://`: anyone on the LAN who captures them can replay the token, so the docs tell users to keep it on a trusted network. Public-server phase: TLS via a reverse proxy (`wss://`), per-user tokens bound to a Java account via an in-game `/tabletop link` command, and the region subscribe restricted to permitted areas. Asset delivery (§3.14) is off by default and, when on, needs `auth.token` and a private, link-local or loopback address, reads only three fixed file names from one folder, and is paced per headset; it is meant for an operator's own files and headsets only.
