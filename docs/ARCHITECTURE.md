# ARCHITECTURE.md — tabletop-craft-ar

A live Java-edition block world shown as a miniature on a real table in Quest 3 passthrough AR. Java players see the headset user as a giant inside the world.

Related: idea file [VR-7](https://github.com/NickStassen/ideas/blob/master/vr/07-minecraft-ar-tabletop.md) and sister project [ironman-quest3-hud](https://github.com/NickStassen/ironman-quest3-hud), which has the Unity/Meta XR setup this project reuses. The wire format is in [PROTOCOL.md](PROTOCOL.md), the phases in [PLAN.md](PLAN.md), and the sources in [RESEARCH.md](RESEARCH.md).

## 1. Components

```
 Java players (LAN) ──MC protocol──▶ ┌────────────────────────────┐
                                    │ Paper server 26.3          │
                                    │  └ tabletop plugin (Java25)│
                                    │     ├ RegionExporter        │
                                    │     ├ BlockChangeTracker    │
                                    │     ├ PlayerBroadcaster     │
                                    │     ├ GiantAvatar           │
                                    │     └ LinkServer (WS :8765) │
                                    └──────────────┬─────────────┘
                                         JSON / WebSocket (PROTOCOL v1)
                                                   │
                       ┌───────────────────────────┴─────────────┐
                       │ Quest 3 Unity app        │ tools/fake-quest│
                       │  passthrough + MRUK table│ (Python, CI/box) │
                       │  greedy mesher + atlas   │                  │
                       └──────────────────────────┴─────────────────┘
```

The Quest has no Minecraft account and never speaks the game protocol in v1.

## 3. Server plugin

### 3.1 Threading rules (hard)
- The Java-WebSocket server runs its own selector/worker threads. **No Bukkit API calls on those threads.** Every inbound message is parsed there (pure JSON → record) and then handed over:
  - poses go into an `AtomicReference<Pose>` latest-value slot that the main-thread tick task reads (so stale poses are dropped for free);
  - `subscribe`, `avatar_config` and similar go into a `ConcurrentLinkedQueue<Command>` that the main thread drains each tick.
- Outbound: main-thread code builds a payload object and calls `conn.send(String)` (Java-WebSocket's `send` is thread-safe). JSON serialization of large snapshots happens **off** the main thread.
- One repeating task, `runTaskTimer(plugin, 1, 1)`, drives the tick work: drain commands, apply the latest pose to the avatar, flush the batched block changes, and send player positions every 2 ticks.

### 3.2 RegionExporter (chunk_snapshot)
1. On the main thread, for each chunk that overlaps the region, take `chunk.getChunkSnapshot(false,false,false)`. Paper copies the section palettes here; that's cheap (about 2 chunks × 4 for 32x32). If a chunk isn't loaded, load it with `world.getChunkAtAsync(x,z)` first.
2. Async (`runTaskAsynchronously`): walk the region in yzx order with `snapshot.getBlockData(lx, y, lz)`, build the palette and RLE (PROTOCOL §6), serialize the JSON and send it. `ChunkSnapshot` is immutable and documented as safe to use off-thread.
3. Snapshot ids are per connection. Block changes that arrive while a snapshot is being built are buffered and replayed against the new `snapshot_id`.
4. Light and biomes (PROTOCOL §4.5.1) are read only when a session on that region has `light_v1` / `biomes_v1`: `getChunkSnapshot(false, biomes, false, light)` (Paper's 4-argument form; without extras it now skips copying light, which made the main-thread step 3-4x cheaper), and the same async walk packs `sky << 4 | block` per block and samples one biome per 4x4x4 cell. Climate (`World#getTemperature/getHumidity`) is looked up on the main thread once per biome key and cached. The light and biome JSON is encoded on the outbound executor (`RegionReader`, `BiomeGrid`, `Protocol.addExtras`).

### 3.3 BlockChangeTracker (block_update)
- Event listeners at MONITOR priority with ignoreCancelled: `BlockPlaceEvent`, `BlockBreakEvent`, `BlockPhysicsEvent` (sampled), `BlockFromToEvent`, `BlockBurnEvent`, `BlockFadeEvent`, `BlockFormEvent`, `BlockSpreadEvent`, `LeavesDecayEvent`, `EntityExplodeEvent`, `BlockExplodeEvent`, `BlockPistonExtendEvent`/`RetractEvent`, `EntityChangeBlockEvent`. Events fire **before** the change, so record only the *position* and read the state at end of tick (in the next tick task, 1 tick later).
- Safety net: every 20 ticks, re-snapshot the region's chunks async and diff them against the last sent state. That catches `/fill`, `/setblock` and WorldEdit. It's cheap at this size (65k comparisons).
- Coalesce by position. Emit one `block_update` per tick; past 4096 changes, send a new snapshot instead.
- Light: for `light_v1` sessions the diff also compares packed light against what the session last got and sends changed cells in `block_update.light` (possibly with no block changes). Light settles a little after the change event, so a change event also schedules a second diff 4 ticks later; past 16384 light changes the session gets a new snapshot.

### 3.4 PlayerBroadcaster
Every 2 ticks: for online players in the region's world within the region's XZ bounds plus 16, send pos/yaw/pitch/sneaking. The skin URL comes from `player.getPlayerProfile().getTextures().getSkin()` and goes out once per UUID, with `skin_model` (`wide`/`slim`, from `getSkinModel()`). Offline-mode servers have no textures, so `skin` is null there.

### 3.5 GiantAvatar — v1 design (decision)
**Use a `Mannequin` entity (Paper ≥1.21.9) for the body and head, scaled with the `SCALE` attribute, plus two `ItemDisplay` entities for the hands.**

- Body: `world.spawn(loc, Mannequin.class, m -> { m.setProfile(ResolvableProfile...); m.setImmovable(true); m.setAI(false); m.setGravity(false); m.setInvulnerable(true); m.setPersistent(false); m.getAttribute(Attribute.SCALE).setBaseValue(s); })`. It renders with the real player model and skin, and the server does the networking to all Java clients, so no NMS or packets are needed.
- Scale: the "true" giant scale is `s_true = (user_height_m / block_size_m) / 1.8` (a scale-1 player is 1.8 blocks tall). At 1 cm/block a 1.75 m person would be about 175 blocks tall, far above the attribute cap (16 → 28.8 blocks), so the scale is clamped to `max_scale`; `avatar_state.note` reports the clamp.
- **Placement** (`config.yml` `avatar.placement`, pure maths in `GiantPlacement`, unit-tested):
  - `ground` (default): the giant stands on the terrain under the headset. X/Z = the head pose mapped to the world (`origin + p / block_size_m`), clamped into the region's X/Z bounds (0.5 block inset). Feet = the highest `MOTION_BLOCKING_NO_LEAVES` surface over its footprint (the centre column and four columns half its width out, so it neither sinks into a hillside nor stands on a tree canopy). Head yaw/pitch follow the headset. The hands keep the user's real head-to-hand offset in metres, scaled by `giant height in blocks / user_height_m`, so arm movements read naturally at any table scale. Why: with exact mapping and a small block size (or the user standing back from the table) the giant ended up 100+ blocks away and high in the air, out of the Java clients' entity view range.
  - `exact`: the head is at the mapped head position and the hands at the mapped hand positions; the feet hang 1.62 × scale below the head (never under the world floor).
- Motion: the target placement is eased in per tick (`avatar.smoothing`, default 0.5; jumps over 16 blocks snap), head yaw takes the shorter way round, and the plugin keeps stepping toward the last pose until it has caught up. Java clients interpolate living-entity moves over 3 ticks on top. The body yaw lags the head by at most 50°, like a player. Hands: `setTeleportDuration`/`setInterpolationDuration` (`avatar.interpolation-ticks`, 2) and `Transformation` scale `0.3 × s`, billboard FIXED.
- Chunks: the giant's entities are non-persistent, so moving them into an unloaded chunk deletes them. The plugin keeps plugin tickets on the region's chunks and on the chunks of the giant's last pose; a target chunk that isn't loaded is loaded with `getChunkAtAsync` and ticketed as soon as it completes (otherwise, with no player nearby, it unloads before the next tick), and the giant holds still until then. Ground heights are only read from loaded chunks.
- Skin: `skin_player` from `avatar_config` (a blank value falls back to `avatar.skin-player`). The Mannequin first gets a name-only (dynamic) profile, which game clients since 1.21.9 resolve themselves. The plugin resolves the name off the main thread with `PlayerProfile.complete(true, true)` (online lookup even on an offline-mode server), falling back to the Mojang API for name → UUID, then switches the Mannequin to a static profile with the signed textures, sets `skin_resolved` and sends `avatar_state`; a failure sends `error skin_failed`. Results are cached per name.
- Lifecycle: spawn on `avatar_config{enabled:true}` (or the first pose), remove on disable, disconnect (+10 s) or plugin disable. Mark the entities non-persistent so a crash never leaves giants behind.
- Fallback if Mannequin misbehaves: a giant `ItemDisplay` player head (`Transformation` scale works for any size) plus the hand displays. No Citizens or ProtocolLib in v1 (RESEARCH §1.3).

### 3.6 LinkServer
`WebSocketServer` subclass bound to `config.bind` (default `0.0.0.0:8765`), `setReuseAddr(true)`. It's started in `onEnable` on its own thread and stopped in `onDisable` with `stop(1000)` (close code 4005 to clients). One `Session` object per connection: state machine `AWAIT_HELLO → READY → CLOSED`.

## 4. Quest app

- Base: copy the HUD repo's Unity 6000.0.84f1 + Meta XR Core/MRUK setup and its Project Setup Tool flow. Built-in render pipeline. OpenXR or the Oculus XR plugin, as the HUD repo did. Android IL2CPP ARM64.
- Scene: an `OVRCameraRig` with passthrough enabled (`OVRPassthroughLayer`, underlay), the MRUK prefab with **Load Scene on Startup**, and the `USE_SCENE` permission.
- Placement: after `MRUK.Instance.SceneLoadedEvent`, find the anchors labeled `TABLE`. Pick the nearest to the head and use `PlaneRect` (or the top of `VolumeBounds`). `TabletopAnchor` goes to the plane's center, rotated so its local +Y is the table normal. Fallbacks: no scene or no table → the user places the world with a controller raycast against `EnvironmentRaycastManager` or the floor at 0.75 m. A grip on both controllers moves, rotates or scales it.
- Rendering:
  - **Mesher:** a greedy mesher per 16x16x16 sub-volume (so `block_update` only rebuilds one sub-mesh). It culls faces against neighbors, and faces only merge when they have the same texture, tint and texture rotation. Greedy UVs are in block units from the section-local corner, in vanilla's per-face orientation (grass fringe up on every side), so merged quads tile exactly like single blocks. Only full cubes and fluids go through the greedy path. Everything else is drawn from its block model (below). Without a pack there are no models, and non-cube states fall back to placeholders from a name-based rules table (a cross quad or a half block). 32x64x32 makes at most 8 sub-meshes.
  - **Block models** (`World/BlockModelBaker.cs`, `World/BlockModels.cs`, `World/ResourcePackAtlas.Models.cs`): with a pack, each palette state's model is baked on the main thread the first time the renderer prewarms it (`Atlas.Face`). The baker handles blockstate `variants` (property match, the first entry of a weighted list, `x`/`y` rotation, `uvlock`) and `multipart` (every part whose `when` matches, including `OR`/`AND` and `a|b`), the model `parent` chain with `#texture` variables (26.x `{"sprite", "force_translucent"}` objects too), and elements with `from`/`to`, per-face `uv` (default from the bounds), `rotation`, `cullface` and `tintindex`. Element rotation can be axis/angle/origin/`rescale` or 26.x `x`/`y`/`z` angles. The result is a list of quads in block units with UVs inside the texture layer (0..1, so no shader change), plus a 16x16 coverage mask per side. Classification (`BlockRules.SetShape`) then follows the model, not the name. Six whole boundary faces with cullfaces (or an opaque shell with hidden inner faces, like powder snow) make a full cube. It stays greedy, with its x/y-rotated textures and a `FaceKey.UvMap` for rotated faces such as sideways logs. Cut-out or translucent cubes (copper grates, frosted ice) become `TransparentCube` so they don't hide neighbours. Anything else becomes `BlockShape.Model`, and `BuildSpecials` emits its quads on the worker threads (`BlockModelMesher`). A face with a cullface is dropped when the neighbour is an opaque cube, when the neighbour's model covers that side (snow layers, slabs and stairs side by side), or, for translucent faces, when the neighbour is the same block (joined glass panes). Opaque and cut-out faces go to the alpha-tested submesh; faces with partially transparent textures or `force_translucent` go to the blended one. Inside-out helper elements (`from > to`) are kept only for see-through textures (spawner cages). Block entities have no model geometry in vanilla, so chests, banners, heads, shulker boxes, decorated pots, conduits, end portals and copper golem statues get simple boxes from their particle texture (banners use the matching wool, heads a flat colour), and bells get a body under their frame. Redstone dust and stems take their state colour, not the biome tint. Workers only read baked data. A worker that meets a palette entry the main thread hasn't prewarmed yet (a race with `block_update`) gets an uncached flat colour, and that section is meshed again after the next prewarm.
  - **Atlas:** runtime-built from a **user-supplied** resource-pack zip (or the user's own `client.jar`) copied to the headset's app storage (`/sdcard/Android/data/<pkg>/files/pack.zip`). Read `assets/minecraft/blockstates/*.json` → `models/block/*.json` (resolve the `parent` chains and `textures` variables) → PNGs, then pack them with `Texture2D.PackTextures` and point clamp filtering. Greedy-merged faces need tiling, so use a `Texture2DArray` (one 16x16 layer per texture) with UVs in block units and wrap/repeat instead of a 2D atlas. That avoids atlas bleeding on merged quads. Without a pack, the app colors faces from a built-in flat color table, so it works with zero Mojang assets.
  - **Fluids** (`FluidMesher`, engine-free, on the meshing workers, run last in `BuildSpecials`): fluids no longer take the placeholder or greedy-cube path. A cell holds water if it is water, has `waterlogged=true`, or is kelp, kelp_plant, seagrass, tall_seagrass or bubble_column. The fluid is drawn in addition to the block. Faces between cells that hold the same fluid are culled, as are faces hidden by a full opaque face of the cell's own block or of the neighbour (`FluidRules.FullFaces`). Surface heights follow vanilla `LiquidBlockRenderer`. Flat faces are greedy-merged, and UVs come from positions so merged or lowered faces tile instead of stretching. Water goes last into the transparent submesh, so it blends over the plants inside it; lava goes into the opaque submesh. Fluids use the faces of `minecraft:water`/`minecraft:lava`, which the renderer prewarms on the main thread. `FluidMesher.WaterColor` gives the per-biome water colour (BlockShading).
  - **Animated textures** (`TextureAnimation` parses `.png.mcmeta`; `ResourcePackAtlas.Animation.cs`): an animated texture keeps one atlas layer, so meshes and shaders don't change. All its frames go into a second `Texture2DArray` (the frame store). `Animate()` runs each frame from the renderer and follows game ticks (20/s). When a texture's frame changes, it copies that frame into the atlas layer with `Graphics.CopyTexture` (GPU to GPU, 1 KB at 16 px). Interpolated animations are blended on the CPU into a one-layer staging array and copied the same way. The atlas is only re-uploaded when new textures arrive.
  - **Vertex colours: biome tint × light × AO** (`World/BlockShading.cs`, `World/BiomeColors.cs`; the contract is at the top of `GreedyMesher.cs`). The atlas only decides *which* tint a face takes (`FaceKey.Tint`: grass, foliage, dry foliage, water, from the model's `tintindex` and vanilla's per-block rules; spruce/birch leaves, lily pads, stems and redstone get fixed colours). The mesher resolves the colour per block from the server's 4x4x4 biomes: override colours or the pack's `colormap/{grass,foliage,dry_foliage}.png` at the biome's temperature/downfall, swamp/mangrove grass from vanilla's seed-2345 simplex noise, dark-forest grass darkening, per-biome water, blended over 5x5 columns like vanilla's default biome blend. Light follows vanilla's smooth lighting: per vertex, the 4 cells in front of the face are averaged (`smoothBlend`) and looked up in the 26.x lightmap at noon, times AO from the 3 neighbouring occluders. For AR the lightmap uses vanilla's "Bright" setting and is rescaled so light level 0 shows at 0.2 (`min_light`) instead of near black; everything outside the region counts as open sky-lit air, so the cut sides read like daylight cross-sections and caves cut by the edge brighten towards the cut. Model quads (`BlockModelMesher`) use the same helper: axis-aligned faces get the smooth light/AO of their block face (bilinear for partial faces, like vanilla's partial-face weights), rotated faces (crosses, 22.5°/45° elements) the block's own light, and tinted faces the biome colour. Fluids are lit like vanilla `LiquidBlockRenderer`: one light per face, the max of the cell and the cell above, no AO, and per-biome water through `FluidMesher.WaterColor`. Faces merge only when their 4 corner colours are equal and constant along the merge direction, which costs about +24-38% faces in total on real terrain with the pack's models and water (greedy faces +55-66%; model and fluid faces barely change; TESTING.md "Lighting with models and water"); `smooth_lighting: false` in `tabletop.json` keeps one light value per face (+4-17%). `AreaMath.LightFactor` (x1.35 smooth, x1.15 flat) scales the area-setup estimate to match. The shaders multiply vanilla's per-direction face shade (top 1.0, bottom 0.5, north/south 0.8, east/west 0.6) and leave diagonal faces (cross plants) unshaded, as vanilla does. Without light/biome data (an older server) colours are exactly the old fixed tints, unlit.
- Players: Minecraft-style figures (`PlayerMarkers` → `PlayerFigure`): six boxes with the game's model sizes and skin UV layout including the second layer (`PlayerModel`, from the game's `PlayerModel`/`ModelPart.Cube`), 1 px = 1/16 block. Positions, yaw and pitch ease toward the 10 Hz samples in world coordinates; `PlayerAnimation` (engine-free) adds limb swing from horizontal speed, idle arm bob, body yaw that lags the head (max 50°) and turns toward the walking direction, and the sneak pose. Skins (`PlayerSkins`): the `skin` URL (textures.minecraft.net only, fetched over https with `UnityWebRequestTexture`, cached per URL, legacy 64x32 skins converted as the game does), else the default skin the game picks for that UUID from the user's `pack.zip`, else a plain-colour skin. Shader `TabletopCraft/PlayerSkin` (unlit, alpha test, no culling, the game's fixed two-light entity shading), shipped through `Resources/TabletopPlayer.mat`. The parts are figure-space boxes (faces +Z, right hand +X), so only the feet position goes through the Z mirror; Minecraft yaw θ becomes a Unity Y rotation of 180° + θ.
- Moving around (PROTOCOL.md 4.17-4.18, QUEST_SETUP.md Part H): the region has a view margin; `XR/NavController` + the engine-free `World/NavState` slide the visible window inside it (left stick) and request the region shifted by whole 16-block sections. `Shaders/TabletopClip.cginc` discards geometry outside the window (global `_TabletopClip`, world → box), and `World/ClipCaps` + `CapMesher` mesh the six cut faces from the block slices they cross so the box looks solid. Snapshots decode on a worker (`World/SnapshotAssembler`, `Net/SectionedSnapshot`); `World/SectionPlan` decides which section meshes survive a shift, and `TabletopRenderer.OnSnapshot` re-keys them (meshes are built relative to their section corner) or keeps the old meshes until a new region is fully meshed. The server sends `sections_v1` snapshots (parts under 1 MiB, deltas with only the new or changed sections) to clients that ask for them.
- Network: `LinkClient` on a background task with `ClientWebSocket`, an inbound `ConcurrentQueue<string>` drained on the main thread, a 30 Hz pose sender from `Update` (head = center eye, hands = controller anchors or hand-tracking wrists), and auto-reconnect with backoff. Hold the Wi-Fi low-latency lock as in the HUD repo.

## 5. Networking/latency notes (from ironman-quest3-hud)
- LAN unicast only. Router AP isolation must be off, and the plugin port (8765/tcp) has to be open on the server PC's firewall.
- Measured in the literature: about 63–106 ms end to end PC↔Quest over TCP. That's fine for a giant whose motion is interpolated over 2 ticks (100 ms).
- Quest Wi-Fi can deliver traffic in bursts; the server's latest-pose-per-tick slot absorbs that.
- The protocol's `ping`/`pong` gives RTT; the Quest logs it to logcat (`adb logcat -s Unity`).

## 6. Security (LAN v1, public later)
Shared token in `hello`, bind address configurable, per-connection rate limit on poses. Public-server phase: TLS via a reverse proxy (`wss://`), per-user tokens bound to a Java account via an in-game `/tabletop link` command, and the region subscribe restricted to permitted areas.
