## What this is
A Paper plugin streams a box of blocks, player positions and block changes over a JSON WebSocket to a Quest 3 Unity passthrough app, which renders it as a table-top miniature. The Quest sends head and hand poses back at about 30 Hz, and the plugin drives a giant avatar that Java players see: by default a floating player head and two hands (ItemDisplays), or a Mannequin with the SCALE attribute (`avatar.placement`; Bedrock players get a Mannequin). The Quest has no game account and never speaks the game protocol.

- **Area setup:** `region_request`/`region_query` → `region_changed`/`region_info`. The region is shared by all headsets, and the last writer wins. Caps come from config.yml `max_region`. The plugin reads regions asynchronously: chunks load via getChunkAtAsync, ChunkSnapshots are taken on the main thread, and the walk runs on a worker, keeping main-thread time under 3 ms. Diffs work the same way. Quest side: `XR/AreaSetupMode.cs` (input, wireframe; verified on the headset) drives the engine-free `World/AreaSetupState.cs` and `World/AreaMath.cs` (fit and budget; tested in Tests~). `TabletopRenderer` meshes on worker threads after prewarming the atlas on the main thread. Never call `ResourcePackAtlas.Face` for an unseen state off the main thread.
- **Moving around:** left stick glides the visible window (left grip + stick = up/down, right stick X turns; triggers and B stay free for block editing) inside a region with a `view_margin` that grows with the visible width (32 below 256 wide, 48 at 256, `AreaSizing.MarginByWidth`; area setup asks for 16 and the first glide grows it); shifts are whole 16-block sections, moved several sections ahead while gliding steadily (lookahead), sent by the plugin as `sections_v1` deltas (PROTOCOL.md 4.17-4.18). The plugin reads only the sections a move adds and copies the rest (`RegionReader`/`RegionData`), so a one-section shift at 288 wide is ~50 ms in one tick; the headset meshes the margin only near the window. Measure gliding with `Tests~ --live-glide URL` (blocks/s per width). Engine-free: `World/NavState`, `SectionPlan`, `SnapshotAssembler`, `CapMesher`, `Net/SectionedSnapshot` (tests in `Tests~/NavTests.cs`). Unity: `XR/NavController` (input, RegionRoot, global `_TabletopClip`), `World/ClipCaps` (cut faces), `TabletopRenderer.OnSnapshot` (re-key or keep old meshes). Block shaders must keep the `[nav]` clip lines (`TabletopClip.cginc`, TEXCOORD7). The session palette in the plugin is touched only on the outbound thread. Check shaders headless with `-executeMethod TabletopCraft.EditorTools.ShaderCheck.Run`; measure with `tools/nav_e2e.py` and `Tests~ --measure-nav`.

## First hardware session checklist
Current flow (v1.1.0 and later; docs/QUEST_SETUP.md "Store install", docs/RELEASING.md section 6). Record what you verify in `docs/OVERVIEW.md` Status and `docs/TESTING.md`.
Prereqs (human): Minecraft: Java Edition 26.3 started once in the launcher on the server PC (the plugin builds the headset's game files from it), the Quest 3 on the same Wi-Fi as the PC.
1. **Server:** download `tabletop-server-starter-<version>.zip` from the latest GitHub release, run `start.bat` (Windows) or `bash start.sh`, accept the EULA. To test a local plugin build, pass `--plugin-jar` / `-PluginJar`. Windows: the network must be Private for the firewall rules (the starter says so when it is Public).
2. **App:** install from the store beta (invite link in QUEST_SETUP.md; BETA serves the promoted build) or sideload the release APK: `adb install -r tabletop-craft-ar-<version>.apk` (Developer Mode). A new auto-release lands on the Meta ALPHA channel first. A self-built, debug-signed APK must be uninstalled before a release-signed one can be installed, and vice versa.
3. **Pair:** start the app at a table; it finds the server on the LAN and shows a 6-digit code. Run `tabletop pair <code>` in the server console. `adb logcat -s Unity | grep Tabletop` shows LINK up and the first snapshot.
4. **Game files:** the plugin builds `pack.zip`, `entity_models.json` and `sounds.zip` from the PC's install and paired headsets download them once (about 75 MB; Info tab `ASSETS` line). If the server logs `ASSETS auto: no Minecraft 26.3 found`, ask the human to start 26.3 once, then `tabletop assets rebuild`.
5. **Table and area:** confirm MRUK detects the table and the area wireframe snaps to it; resize, auto-fit, try small and large areas and note FPS.
6. **Gameplay checks:** textures and tints (Info tab `PACK yes`), live block diffs from a Java client, the giant avatar following head and hands, sound.
7. **Profile** with OVR Metrics; tune the 250k-face soft cap if needed.
8. **Promote** once the ALPHA build passed on the headset: `gh workflow run promote.yml --ref master -f version=X.Y.Z` (see "Releases" below).
Developer fallback (QUEST_SETUP.md appendix Parts A-E): build the plugin and APK yourself (`TabletopBatch.BuildApk`), `adb install`, and push hand-made `pack.zip`, `entity_models.json` and `sounds.zip` to `/sdcard/Android/data/com.tabletopcraft.ar/files/`, or serve them from `assets.dir` (Part P). Never commit the jar or those files.
CI: `.github/workflows/ci.yml` (Gradle tests, ruff + pytest, the engine-free C# tests, the Windows starter). Releases: `auto-release.yml` (calls `release.yml`) and `promote.yml`.

## Protocol rules
- **Versioning (from v1.0.0, semantic):**
  - Write project versions as `vX.Y.Z` in docs and messages (v1.1.0, not 1.1 or v1.1); `v1.0.x` / `v1.x.y` for a range. The wire field `v` (protocol v1) is separate.
  - One version for plugin `version` (build.gradle.kts), the app's `bundleVersion` and the PROTOCOL.md version line, all from `VERSION`.
  - Patch (v1.0.x) for fixes, minor (v1.x.0) for new features that old plugins/apps can ignore (new optional fields, new messages behind caps), major (v2.0.0) for anything that breaks a plugin/app of the same major version. Every protocol change gets a changelog entry.
  - Before v1.0.0 there was no backwards compatibility (v0.x.y versions just had to match).
- **Releases:** one `VERSION` file at the repo root is the single source: Gradle reads it for the plugin, and `TabletopBatch.BuildApk` sets the app's `bundleVersion` and versionCode from it. Versions are bumped by `auto-release.yml`, never by hand (docs/RELEASING.md section 6):
  1. every push to master that changes shipped code (`quest-app/Assets`, `Packages/manifest.json`, `ProjectSettings`; `server-plugin/src/main`, `build.gradle.kts`; `server-starter`) becomes the next version: `tools/release/auto_release.py` writes `VERSION`, the PROTOCOL.md header and an automatic changelog line, the ProjectSettings version lines and `docs/release-notes/vX.Y.Z.md`, commits `release: vX.Y.Z` (with the skip keyword), tags it and pushes both, then `release.yml` builds the plugin jar, the server starter zip and the release-signed APK, creates the GitHub **pre-release** and uploads the APK to the Meta **ALPHA** channel;
  2. use `[minor]` / `[major]` in a commit message for a feature or a breaking release (patch otherwise) and `[skip release]` to hold a push back; these keywords count anywhere in a message, so never quote them by accident;
  3. a protocol change still needs a changelog line written in the same commit: `- **vNEXT: ...**` (the release gives it the version); hand-written release notes go in `docs/release-notes/vNEXT.md` (docs/release-notes/README.md);
  4. to release master by hand: `gh workflow run auto-release.yml --ref master -f bump=auto` (or `patch`/`minor`/`major`); preview locally with `python3 tools/release/auto_release.py plan --event workflow_dispatch`;
  5. check the ALPHA build on a headset, then promote: `gh workflow run promote.yml --ref master -f version=X.Y.Z` (ALPHA to BETA, and the GitHub release becomes the latest one, which the server starter downloads from).
  By hand (fallback): `TabletopBatch.BuildReleaseApk`, `tools/release/upload_quest.sh`, `promote_quest.sh` (RELEASING.md sections 3-5). Never attach the client jar, pack.zip, entity_models.json, sounds.zip or a keystore.
- `docs/PROTOCOL.md` is the contract for the plugin, Quest app and tools. Golden examples are in `tools/fixtures/`; Java (`FixtureTest`) and Python tests read them.
- Frames: tabletop frame is right-handed, metres, axes parallel to the world, origin at the region's local (0,0,0) corner. Unity conversion is `p=[ux,uy,-uz]`, `q=[-qx,-qy,qz,qw]` (PoseSender/TabletopPose). Mesh vertices are mirrored on Z and triangles re-wound in TabletopRenderer.
- Known gaps vs the spec are listed in `docs/TESTING.md` under "Spec deviations".

## How to debug
- Server: `/tabletop status`, `/tabletop avatar status` (logs `AVATAR_STATE` / `AVATAR_ENTITY`). Set `debug.avatar-state: true` to stream entity positions to clients.
- Quest: `adb logcat -s Unity | grep Tabletop`. The block menu's Info tab (left ≡) shows LINK, RTT, WORLD, PACK, TABLE and POSES; `"show_hud": true` in tabletop.json (or Show HUD in the Info tab) brings back a small head-locked copy.
